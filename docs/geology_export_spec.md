# Спецификация экспорта геологии из tNavigator (для анализа «геология ↔ отклик»)

Статус: согласовано с пользователем (cowork-сессия, 2026-06-12). Выбран вариант
«и well-block таблица, и кубы»: well-block — сейчас (уровень 1), кубы — вторым
шагом (уровень 2, связность).

Мотивация: SRC²-анализ (outputs/qc/well_parameter_influence.csv) показал, что
9 параметров варьирования объясняют лишь 4–22 % дисперсии откликов скважин;
остальное — реализация куба фаций. Цель экспорта — извлечь из уже рассчитанных
150 моделей геологические дескрипторы реализации и связать их с добычей тем же
аппаратом (корреляции, SRC², бутстрап-стабильность, порог 3/√N).

## Куда класть файлы

```
data/geology/wellblocks/   # уровень 1: по одной таблице на модель
data/geology/cubes/        # уровень 2: по два куба на модель (фации, kx)
```

Имена файлов должны содержать seed модели — он же суффикс листа в
«Показатели динамики.xlsx» (правило связки: round(SEED) из
models_near_adapted_centroids.xlsx; проверено 150/150):

```
wellblocks/wb_<seed>.csv         # пример: wb_2149.csv
cubes/facies_<seed>.grdecl       # ключевое слово FACIES (целые коды)
cubes/permx_<seed>.grdecl        # ключевое слово PERMX (мД)
```

## Уровень 1 — well-block таблица (сейчас)

Одна CSV-таблица на модель: все ячейки, пересечённые стволами 23 скважин
(17 producers WELL*, 6 injectors INJ*). Обязательные колонки:

| колонка | тип | описание |
|---|---|---|
| well | str | имя скважины как в dynamics-файле (WELL1 … INJ6) |
| i, j, k | int | индексы ячейки |
| facies | int | код фации ячейки (канал/пойма; указать словарь кодов в README рядом) |
| ntg | float | NTG ячейки (если свойство есть; иначе опустить) |
| permx | float | проницаемость, мД |
| dz_eff | float | эффективная (вскрытая) толщина ячейки вдоль ствола, м |
| perforated | 0/1 | вскрыта ли ячейка перфорацией (если доступно; иначе считаем все 1) |

Допустим любой разделитель (`,` или `;`), кодировка UTF-8. Размер ожидается
~150 файлов × десятки строк — мегабайты суммарно.

Из этой таблицы будут посчитаны дескрипторы (модель × скважина):
`net_sand_penetrated` (Σ dz_eff по канальным фациям), `kh_penetrated`
(Σ permx·dz_eff), `frac_channel_cells`, `mean_ntg_along_well` — и затем:
R²-uplift против θ-only (ожидание: 0.1–0.2 → 0.5–0.8), корреляции с
накопленной добычей/обводнением при том же пороге 3/√N и бутстрапом B=2000,
механистическое объяснение связей AZIMUTH→WELL7/WELL3A (через попадание
канала в ствол).

## Уровень 2 — кубы свойств (вторым шагом)

По каждой модели два куба в GRDECL/ASCII (один и тот же грид у всех моделей):
`FACIES` (целые коды) и `PERMX` (мД). Дополнительно один раз: геометрия грида
(COORD/ZCORN или хотя бы NX NY NZ + DX DY DZ) и траектории/перфорации скважин
(welltrack или таблица well → список (i,j,k)).

Анализ: связные геотела песка (scipy.ndimage.label, 26-связность по умолчанию;
чувствительность к 6-связности проверим), на их основе — `connected_sand_volume(w)`
для каждой скважины, бинарная матрица связности скважина–скважина и
скважина–нагнетание. Гипотеза для статьи: связность с INJ объясняет водяные
метрики (width_ratio по воде 2.22 против 1.47 по нефти).

## Ограничения и правила

- tNavigator запускает пользователь; пайплайн не вызывает симулятор (CLAUDE.md).
- Входные Excel-файлы не модифицируются; новые данные кладутся только в data/geology/.
- Перед коммитом результатов анализа добавить фичу в feature_list.json
  (предложение: `geol-001-wellblock-descriptors`, `geol-002-connectivity`).
- Сами расчёты новых прогонов не нужны — только экспорт уже посчитанных моделей.
